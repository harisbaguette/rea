# 같은 기능을 만드는 설계

## 실사 변환을 먼저 확인할 때

처음 결과물은 웹앱으로 잡는다. 카메라 입력, 참조 이미지 선택, 변환 시작·중단, 원본과 결과 비교만 두면 모델 품질과 비용을 판단할 수 있다. 쇼핑몰 이미지 탐색과 크롬 확장은 그다음에 붙인다.

| 부분 | 맡을 일 |
| --- | --- |
| 브라우저 | 카메라 허용, 이미지 선택, 입력·결과 재생, 대기·실패·중단 상태 표시 |
| 자체 서버 | 사용자별 사용 한도, 접속 제어, 단기 클라이언트 토큰 발급 |
| Decart SDK | WebSocket 제어 통신과 WebRTC 영상 연결, 참조 이미지·프롬프트 갱신 |
| 모델 | 옷은 Lucy VTON, 인물·헤어·장면은 Lucy 2.5 |

영구 API 키는 서버에만 둔다. 브라우저는 연결 직전에 단기 토큰을 받아 SDK에 전달한다. 토큰의 만료와 이미 시작한 세션의 종료는 다르므로, 비용 상한에는 서버의 세션 시간 제약도 필요하다.

아래는 흐름을 설명하는 의사 코드다.

```text
camera = 카메라 영상 열기(audio = false)
token = 자체 서버에서 단기 토큰 받기
model = 변환 대상에 맞는 모델 선택
session = SDK로 camera 연결(token, model)
결과 영상 = session의 원격 영상
session에 참조 이미지와 변경 문장 전달
중단 시 session 연결 해제 + camera의 모든 트랙 중지
```

현재 SDK의 `set()`은 세션 상태를 통째로 바꾸므로 유지할 이미지와 프롬프트를 함께 넘긴다. 이미지와 프롬프트를 따로 갱신하다가 이전 설정이 사라지는 경우를 확인해야 한다.

## 처음 비교할 장면

| 장면 | 확인할 결과 |
| --- | --- |
| 정면 → 옆면 → 뒤돌기 | 변환이 따라오는지, 얼굴과 옷이 튀지 않는지 |
| 손으로 얼굴·옷 가리기 | 손이 사라지거나 변환 대상과 섞이지 않는지 |
| 같은 세션에서 이미지 바꾸기 | 새 설정이 반영되고 이전 설정이 남지 않는지 |
| 카메라 거부·네트워크 단절 | 복구 경로가 있고 불필요한 세션이 계속 실행되지 않는지 |
| 중단·탭 숨김·페이지 이탈 | 카메라와 원격 연결이 정리되고 사용량 집계가 끝나는지 |
| 짧은 세션 반복 | 실제 생성 초와 청구 사용량이 맞는지 |

먼저 자기 얼굴이나 이용 허가를 받은 자료로 확인한다. 특정인의 모습으로 바꾸는 서비스는 그 사람의 동의와 합성 결과 표시를 포함한다. 일반 API 약관에는 입력·출력의 학습 이용을 허용하는 조항이 있으므로, 얼굴 영상을 쓰는 제품이라면 학습 제외와 보관 조건을 계약으로 확인해야 한다. 약관 문구만으로 특정 Anywear 세션이 실제 학습에 사용됐다고 단정할 수는 없다.

## 서버 연산 비용을 줄이는 경로

안경·메이크업·얼굴 스티커라면 MediaPipe로 얼굴 위치와 표정을 구하고 브라우저에서 효과를 그리는 방법을 비교한다. 필요한 모델과 렌더링 자원을 자체 제공하고 영상 전송을 없애는 설계를 택할 수 있다.

이 경로에서도 기기의 연산·배터리·초기 모델 다운로드 비용은 남는다. 실사 인물 교체나 새로운 머리카락·장면 생성은 별도의 생성 모델이 필요하다.
